# 项目设计思路

本文从“先用浏览器访问目标网站”开始，记录如何把页面观察转化为采集方案、程序结构和可交付的数据产物。这里描述的是当前 `prts-crawler` 的设计与实现，不是独立的网页前端项目。

## 1. 从浏览器访问网站开始

首先在浏览器打开 [PRTS 干员一览](https://prts.wiki/w/干员一览)，观察用户实际能看到的内容：干员卡片、职业与稀有度筛选、搜索和分页。页面看起来像一张列表，但不能仅凭视觉效果判断数据来自静态 HTML、浏览器脚本，还是服务端接口。

接下来用开发者工具检查页面：

1. 在 **Elements** 中检查列表区域，确认首屏 HTML 没有普通 `<table>`，列表由页面组件渲染。
2. 查找 `#filter-data`，发现页面 HTML 内还包含带有 `data-*` 属性的完整干员数据。由此确认，浏览器看到的分页只是展示层行为，并不代表源站只提供当前页的数据。
3. 在 **Network** 中查看页面请求，并检查页面源码和相关模板，追溯列表字段如何产生。项目的具体抓取验证记录在 [data-sources.md](./data-sources.md)。
4. 对观察到的接口和字段用独立请求验证，比较返回字段、数据完整性、请求数量和响应形式，再决定程序实际使用的入口。

这一步的关键结论是：浏览器负责帮助理解页面和发现数据契约；自动化采集不必模拟点击、滚动或浏览器渲染，应该优先使用已验证、结构稳定的数据接口。

## 2. 从页面观察到采集策略

列表页由 Vue 组件呈现，底层数据来自 Cargo。项目比较了两种可行路径：

- 解析列表页中的 `#filter-data`：可作为接口不可用时的后备方案，但需要处理 HTML 属性和页面标记。
- 调用 MediaWiki 的 `action=cargoquery`：返回字段清晰的 JSON，能一次取得干员索引，更适合作为主路径。

因此索引采用 Cargo API，并保留解析渲染 HTML 的 fallback。干员技能、天赋、模组和档案等详情信息并不都在索引接口中；这些字段保存在各干员页面的 Wikitext 模板里，所以使用 MediaWiki revisions API 分批读取页面源码，再由模板解析器提取结构化字段。头像则先用 `imageinfo` 查询真实文件 URL，再下载文件，避免按文件名猜测存储路径。

整体数据流如下：

```text
PRTS 网站
  ├─ Cargo API ───────────────> 干员索引 JSON
  ├─ MediaWiki revisions API ─> 页面 Wikitext ─> 详情解析
  └─ imageinfo / 媒体 URL ────> 头像与职业图标
                                     │
                                     v
                           合并、规范化、缓存
                                     │
                   ┌─────────────────┼─────────────────┐
                   v                 v                 v
             operators.json   operators.jsonl   Markdown / HTML
```

选择批量 API 而非逐页操作浏览器，主要是为了减少请求、降低对页面布局的依赖，并直接保留可重复处理的结构化输入。列表、详情和媒体来源各有职责，遇到页面展示层改版时，也能分别定位问题。

## 3. 程序结构

项目采用 Python 标准库实现，不引入运行时第三方依赖。代码按数据来源和处理职责拆分：

| 模块 | 职责 |
| --- | --- |
| `config.py`、`env.py` | 解析默认配置、环境变量和 `.env` 文件，统一请求与输出参数 |
| `http.py` | 集中处理 HTTP、超时、gzip、全局限速和可重试错误 |
| `cargo.py` | 查询 Cargo 干员索引，并按站点限制处理分页 |
| `fallback.py` | 主索引接口失败时，从页面渲染 HTML 提取列表数据 |
| `detail.py`、`wikitext.py` | 批量读取页面源码，解析嵌套模板和具体详情字段 |
| `media.py` | 查找头像和职业图标 URL，下载到本地媒体目录 |
| `pipeline.py` | 编排缓存、抓取、数据合并、元信息记录和导出 |
| `export.py` | 将统一数据集生成为 Markdown 摘要和独立 HTML 看板 |
| `cli.py` | 提供分阶段命令、参数覆盖和可读的运行结果 |

`pipeline.py` 将工作拆成 `index`、`details`、`media`、`export` 阶段。这样既能完整运行，也能只刷新索引、跳过图片，或在完全离线时从已有 JSON 重新生成视图。

## 4. 数据建模与产物

采集结果以一个干员一条记录的 JSON 数据集为核心。列表接口提供基础身份、职业、标签和面板信息；详情解析补足技能等级、专精、天赋、模组、基建技能和档案。合并时统一字段名称和类型，并将源站 0 起始的稀有度转换为面向使用者的 1–6 星。

输出按用途分层：

- `index.json` 保存列表抓取结果，便于检查索引来源并复用。
- `cache/wikitext/` 保存原始页面源码，让解析逻辑可以离线迭代，减少重复请求。
- `operators.json` 是完整、可直接消费的结构化数据；`operators.jsonl` 便于逐行处理。
- `meta.json` 记录数量、覆盖率和抓取信息，帮助判断数据是否完整。
- `exports/operators.md` 面向代码审查和版本对比，保持紧凑、易 diff。
- `exports/operators.html` 面向浏览和分享，提供搜索、折叠详情和本地图片，不依赖外部脚本或样式。
- `media/` 保存头像与职业图标，让导出的 HTML 可以随整个数据目录离线查看。

原始输入缓存、规范化数据集和人类可读视图分开保存，是为了让抓取、解析和展示可以分别重跑，不必每次都重新访问网站。

## 5. 可靠性与站点礼貌

浏览器和独立请求验证也暴露了源站约束，例如请求头要求和批量接口的单次上限。实现中因此采用统一 HTTP 客户端，默认设置合适的 `Accept-Language`，使用共享限速器约束并发请求，并对超时、429 和部分服务端错误进行有限次数的指数退避。

同时通过以下措施控制失败影响：

- 优先复用已保存的索引和 Wikitext 缓存，`--refresh` 才强制重新抓取。
- 详情按 MediaWiki 的每批标题数限制分组，批次可以并发，但请求仍受全局限速器约束。
- Cargo 查询失败时尝试 HTML 索引 fallback；结果为空则显式报错，避免把空数据当作成功结果。
- 记录数据来源与覆盖率，便于区分“字段确实为空”和“采集过程不完整”。
- 支持 `--limit` 小样本试跑；通过 `.env` 设置个人 User-Agent 和速率，不建议提高默认请求频率。

## 6. 典型运行路径

```text
浏览器观察页面与接口
  -> 验证 Cargo、Wikitext 和图片 URL 的实际数据契约
  -> 抓取并缓存索引
  -> 批量读取、解析详情模板
  -> 可选下载图片
  -> 合并并规范化数据
  -> 输出 JSON / JSONL / Markdown / HTML
```

常见命令与此流程对应：

- `prts-crawler index`：只更新干员列表。
- `prts-crawler details`：更新列表并补充详情。
- `prts-crawler all`：执行完整流程。
- `prts-crawler export`：不访问网络，使用已有数据重新生成导出视图。
- `--limit N`：限制抓取数量，适合开发和验证。

## 7. 设计边界

本项目聚焦于从 PRTS 获取并整理干员数据，不模拟真实用户登录、不自动操作浏览器，也不尝试绕过站点访问限制。网站模板、Cargo 字段或 API 行为发生变化时，需要重新在浏览器中检查页面和请求，再更新对应的数据源适配器与解析测试。数据和图片的版权仍归原权利方所有，使用时应遵守站点规则。

更细的接口、字段和验证结果见 [数据来源分析](./data-sources.md)；安装、配置和命令说明见 [项目 README](../README.md)。
